- **The post-run integrity check no longer blames a run for another session's commit, and never writes onto another session's branch** (`engine/scout/sandbox/integrity.py`). An owner session that fast-forwarded the vault's `main` mid-run with an approved `.claude/settings.json` change got a "restore" commit on `main` and on every `claude/*` branch other sessions had just made from it, and run health turned red (`run.integrity_restored`).
  - Under Phase 1d (the enforced sandbox with the broker's tightened profile, which leaves the commit broker as the run's only way into git), a protected file is the run's only if a commit the broker recorded for a run touched it. Anything else that changed during the run is one "left alone" log line, not a restore and not a finding. That covers branches and worktrees made during the run, and the index after an owner merge in the vault's checkout. A protected file the run's own commit touched is still put back, even under a later owner commit or a forged author, and health turns red as before.
  - Without that record (Phase 1c, sandbox off, or a commit the broker started without recording it), the check stays conservative, as before.
  - In both cases a restore commit is never written onto a branch another work tree has checked out now. Such a branch is reported as still holding the change (`unrestored`, health red), and the log names the worktree and the paths to check. The vault's own branch is always put back.
