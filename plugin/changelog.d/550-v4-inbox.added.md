- **Delegate inboxes, part one: an agent proposes, the laptop pulls** (#550 V4a1, spec §7.1a; `engine/scout/delegate_inbox.py`, `engine/scout/delegate_proposals.py`). Nothing is applied yet: `inbox apply` is the next PR.
  - `scoutctl delegate inbox <id> --create-repo owner/name` (or `--remote <url>`) links a delegate to its own private inbox repository. Scout binds it by GitHub's numeric repository and owner ids. Before every pull it checks the repository: private, owned by a user, not a fork, no collaborators, no deploy key but the agent's, GitHub Actions and Pages off, and used by no other inbox or mirror. It can't see GitHub Apps; link warns about those that can reach all your repositories. `--create-repo` turns Actions off itself. `--reset` takes the inbox as it is after `inbox_rewritten`, clears the newest-taken mark, and pushes nothing. `--unlink` forgets the inbox.
  - `scoutctl delegate key <id> --inbox` gives the agent a deploy key titled `scout-delegate-inbox-<id>`. Scout refuses unless GitHub records the key as writable. The mirror key stays read-only.
  - `scoutctl inbox propose observation|action` is the agent's side, and is allowed in a delegate checkout. It writes one proposal, `inbox/<id>/<ULID>.json`, in the agent's inbox clone and commits it there; `--push` pushes it. `scoutctl delegate init --inbox <clone>` tells the agent's setup where that clone is, and the env file remembers it.
  - `scoutctl inbox pull <id>|--all` runs on the owner's computer.
    - **The fetch.** Each pull uses a fresh bare repository in `.scout-state/delegate-inbox/` (0700, which runs can't write), and checks nothing out. Git runs with no hooks and with fsck on. It may use only the inbox's own transport, under a remote name no config can target and with only gh's credential helper, with no submodules, no lazy fetch and no replace refs. A file-size limit applies, and a timeout kills git and everything it started.
    - **What it reads.** It reads `main` only, by its sha, never tags. It lists only `inbox/<id>/` and filters out blobs over 16 KiB. Proposal text can't hold controls, invisible or unassigned characters, markup (`[[`, `[#`, `<!--`, `![`, `](`, a task checkbox), or the owner-directive marker. No input can wedge a pull: anything odd is refused as `bad_entry`. `main` must build on the last one this computer saw: the pull deepens at most 256 commits to find it, or refuses with `inbox_rewritten`.
    - **The order.** Every proposal is checked strictly. Each one taken is recorded in `.scout-state/delegate-inbox/state.json`, which is signed; runs can't write anywhere in that folder. Then it is copied to `.scout-inbox/agents/<id>/`, and its ULID goes in a `taken.ledger` there. Last, everything taken or refused is removed from the inbox in one compare-and-swap commit.
    - **Limits.** A pull lists at most 2000 entries and takes at most 50 proposals, and at most 200 a day; the rest stay in the inbox. Nothing is taken twice on this computer, even after a crash. Another computer skips what the ledger lists.
