- **A hung claude behind a live runner shell is no longer taken for a working one** (review of #701; `engine/scout/run_progress.py`, `templates/scripts/scout-lock.sh.tmpl`). The lock reaper counted any write to the run log as progress, but `claude -p` writes nothing until it exits, and on a vault linked to Agnes the lease keepalive appends a line every five minutes for as long as the runner shell lives. So a claude that hung while its shell lived was never judged wedged, and kept the session lock (and every later slot) until something else ended it.
  - **A progress watcher beside every run.** Once a run holds the session lock, `scout-lock.sh` starts `scoutctl progress watch`, on every vault, linked or not. Every `SCOUT_PROGRESS_SAMPLE_SECS` (default 60, at most 600) it samples the runner's session the way the reaper does, but without Scout's own helpers: the lease keepalive, the run brokers, the watcher itself, and anything they start. A helper is a process whose command line starts as the engine running that subcommand; a prompt that merely names one changes nothing.
  - **What counts as progress.** The session made progress when it started or ended a process, such as a tool call, or burned `SCOUT_LOCK_PROGRESS_CPU_SECS` (default 10) of CPU within its last 10 samples. The window slides: a `claude -p` stuck on an API that never answers still burns about 0.08% CPU (measured), which summed since the last progress would reach any threshold within hours. A sample `ps` can't take (an error, a timeout, a table without the runner) counts as neither progress nor stall.
  - **The line.** After each sample the watcher writes how long, in awake time, the session has gone without progress to `.scout-logs/.scout-session.lock.alive`, through a new `mkstemp` file renamed over it, so a link planted in `.scout-logs` is never written through. It stops on the run's EXIT trap. If the runner is killed, the watcher sees the PID gone and removes its line; a reap takes it with the session's process group. An engine older than the template just means no watcher, and nothing in the run log.
  - **The reaper reads that line.** While the holder's line is fresh, its stall is the stall, and the holder is reaped once it passes `SCOUT_LOCK_MAX_AGE_SECS` (7200 s of awake time), with no baseline sample needed. A line is fresh for three samples plus 30 s, never more than 1830 s whatever it says, and never while its time is in the future, so a forged line goes stale like a real one. Every reader opens it without following a link or blocking on a FIFO, and refuses one over 4 KB. Without a fresh line (a runner from before this release, a watcher that died) waiters sample CPU and the process list themselves as before, but the run log no longer counts. The lease keepalive is unchanged: it still renews the lease and still logs each renewal.
  - **Run health says so too.** `scoutctl health` reports `session.no_progress` (yellow) when the live lock holder's fresh line shows a stall past the same ceiling. Health reads `SCOUT_LOCK_MAX_AGE_SECS` from its own environment and the reaper from the launchd job's, so a changed ceiling belongs in both.
  - Existing vaults pick up the runner change with `/scout-update`. Until then, their runs keep the old rule. The run timeout (`agent-runtime exec`) is still off for Claude Code, so the reaper and the app's "Didn't finish" are what bound a hung run.
