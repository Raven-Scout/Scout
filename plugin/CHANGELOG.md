## [Unreleased]

### Added
- **`eval.sh compare-models`: measure a slot on a cheaper model before switching it** (`engine/tests/eval/harness/cli.py`, `engine/tests/eval/harness/verdicts.py`, `engine/tests/eval/harness/report.py`; spec `docs/superpowers/specs/2026-10-13-slot-model-selection-design.md` §8). `compare` scores two git refs on one model and refuses samples from different models, so it could not say whether a scenario holds up on Sonnet. `scripts/eval.sh compare-models <scenario…> [--a opus] [--b sonnet] [--reps N]` runs the working tree on both models, interleaved, and prints the usual per-check verdicts and per-metric medians (turns, tool calls, usage-equivalent cost…) with the models as column headers. A check stable on the reference (`--a`) and missed twice on the candidate (`--b`) is a regression, and the command exits 1. It gives no verdict when both arms turn out to have run the same model (the switch did not take) or one arm mixed models. It runs real sessions on your own Claude login, like `run` and `compare`; it prints the plan and asks first, and more than 10 sessions needs `--many`. CI runs only its tier-0 tests.
- **Choose the Claude model each scheduled slot runs on** (`engine/scout/models.py`, `engine/scout/schedule.py`, `engine/scout/scripts/models_config.py`, `engine/scout/cli.py`, `templates/run-scout.sh.tmpl`, `templates/run-dreaming.sh.tmpl`, `templates/run-research.sh.tmpl`, `templates/scripts/run-outcome.sh.tmpl`, `templates/scripts/write-session-cost.sh.tmpl`; spec `docs/superpowers/specs/2026-10-13-slot-model-selection-design.md`). Every runner used to pass `--model opus`. A slot in `.scout-state/schedule.yaml` can now name its own `model:`, and `models.default` in `scout-config.yaml` covers every slot that names none, plus runs started without a slot (the heartbeat, `/scout-briefing`). A slot's own model wins, then `models.default`, then `opus`; `SCOUT_MODEL` in the environment overrides all three. Values are `opus`, `sonnet`, `haiku` or a full `claude-…` model ID; anything else is rejected with an error naming the slot and the value, by `scoutctl schedule validate` and by the loader. **Nothing changes by default:** no shipped slot names a model and there is no default, so every run stays on Opus until you choose otherwise. New commands: `scoutctl model resolve [--slot KEY]` (what the runners call before each session), `scoutctl model show [--json]` (the default and each slot's model, with where it comes from) and `scoutctl model set-default MODEL` (writes `models.default`, keeping every comment in the file). `schedule list --json` and `schedule show` include `model`. If the engine cannot resolve a model, the run still goes ahead on Opus, and its log says why. Each run's log names its model, and the model is recorded in `run-outcomes.jsonl` rows and the usage tracker's rows, so cost can be split by model. The engine manifest advertises `slot_model_v1`. Existing vaults pick up the runner changes with `/scout-update`.

### Changed
- **The connector health report skips log files that are entirely outside its 14-day window** (#80; `engine/scout/scripts/connector_health_report.py`). Each report used to open and JSON-decode every `connector-calls-*.jsonl` (30 days kept), then throw away the older half row by row. A small index at `.scout-cache/connector-calls-index.json` now records each file's newest row timestamp under its stat key (mtime, ctime, size, inode). A file that is unchanged, and whose newest row is older than the window, is skipped without being opened. Any change to a file changes its key, so the file is read again. File names are never trusted for dates. A file modified in the last 2 s is not recorded. A torn, missing or foreign index is ignored and rebuilt, and an index that can't be written only costs the next report a full read. The report also resolves the configured zone once per run: it used to read the config YAML 11 times per report, once per rendered timestamp. Output is byte-identical, pinned by a golden test with the expected files generated by the previous code. With 30 days × 1,500 rows (6.8 MB), a report takes 0.054 s instead of 0.155 s, and 0.10 s on the first run, which builds the index.
- **`KnowledgeGraph.load()` only re-parses KB files that changed** (#77; `engine/scout/kb/ontology.py`). Every call used to read and YAML-parse every `.md` under the KB: about 1 s per load for 3,000 notes. Parses are now cached per file for the life of the process. Each load re-stats every file and re-parses one only when its mtime, ctime, size or inode changed, so an edit, a same-size rewrite, an atomic replace or a delete is picked up on the next load. A file modified in the last 2 s is re-read every time until it settles, in case the filesystem's timestamps are too coarse to show a second edit. Each hit returns fresh objects. The API and the graph it builds are unchanged. On a 3,000-file KB, a repeat load now takes 0.03 s instead of 1.0 s, and a load after 5 edits takes 0.03 s. The vault's own `knowledge-base/ontology/parser.py` runs as a new process on each call, so this cache does not apply to it, and it is unchanged.

### Fixed
- **`kb-shard-log.py` ships to vaults, and `split-oversized` no longer deletes the file it is about to read or hides the links a split orphans** (`templates/scripts/kb-shard-log.py`, `engine/scout/scripts/bootstrap.py`). The KB log sharder was a vault-only script; install and upgrade now write it to `scripts/kb-shard-log.py` like the other managed helpers, and a vault's own copy is kept, merged or parked as usual. Three fixes come with it. When the index file passed as `file` lived inside the shard directory, the splitter split and deleted it, then the reindex step opened it and failed with a traceback, after the parts were already on disk. It now refuses that case with exit 2 before splitting anything, and rejects a missing index up front. A split removes `<stem>.md`, so every `[[<stem>]]` link dangles, and nothing said so: the command now prints a `REPOINT OWED` block naming each removed stem, with a `grep` that finds the links to it, and exits 3. And a part that outgrew the budget re-split onto its own stem (`<stem>-p01-p01.md`); it now becomes the next free part of its own series and never overwrites an existing one.
- **The connector-call log has a daily size cap and prunes itself** (#66; `engine/scout/connector_calls.py`, `engine/scout/hooks/connector_log.py`, `engine/scout/hooks/session_tool_log.py`). Old days were deleted only when the health report ran, and nothing capped a single day. The ledger now has two bounds:
  - **Daily cap:** a day's file stops growing at 64 MiB, about 150× a normal day. The first row that doesn't fit is replaced by one marker row that records when the cap was hit, and the day's file is closed. Every later row that day is dropped, and the hook says so on stderr. The cap is checked under the append lock, so concurrent writers never overshoot it (beyond the one marker row).
  - **A capped day is visible:** the health report keeps the marker out of its sessions and counts, so it never becomes a fake run with 0 calls. It shows a notice at the top of `connector-health.md` instead: "Call log capped: the YYYY-MM-DD log hit its daily size cap at HH:MM; calls after that were not logged, so that day's counts are low." The report's event payload gains `log_capped_at`.
  - **Pruning:** both writers delete files dated more than 30 days ago when they write a day's first row, so retention holds even with `connector_health` turned off. The report still prunes too. 30 days is more than twice the report's 14-day window. Run health doesn't read these files.

  The Stop hook's transcript replay (`session_tool_log`) now takes the same exclusive lock as the PostToolUse hook. Before, its multi-row writes could interleave with the PostToolUse hook's rows in the same file.

### Security
- **A failed Telegram send no longer prints or logs the bot token** (`engine/scout/scripts/notify_telegram.py`, `engine/scout/redact.py`, `engine/scout/cli.py`, `engine/scout/triggers/`). The token is part of the Bot API URL, and `requests` copies the URL into its errors: a connection failure's message has the path, an HTTP error's message the full URL. `scoutctl notify telegram` printed such a message to stderr, and a trigger's `notify` action wrote it to `.scout-logs/trigger-fires-*.jsonl`. `send()` now re-raises any failure with the token removed from its message, its arguments and the URL it carries, and keeps the same `requests` error type. The CLI, `main()` and the trigger paths also redact the error text they print or record.

## [0.18.1] - 2026-10-13

### Fixed
- **A good Linux install is green, and `install.sh` exits 0** (#449; `engine/scout/scripts/bootstrap_doctor.py`). The doctor checked launchd jobs on every POSIX host. On Linux there is no `launchctl`, so every install got "launchctl unavailable" and came out yellow, and `install.sh` (which exits with setup's doctor code) exited 1. The launchd check now runs on macOS only. On Linux the doctor checks the scout-managed crontab block that `scoutctl schedule install-cron` writes instead: it is red when the block has no schedule tick or no heartbeat line, or when it runs a different vault. The fix hint names the vault (`SCOUT_DATA_DIR=<vault> scoutctl schedule install-cron`). With no `crontab` binary, it warns and skips the check. Other platforms check no scheduler.
- **`scoutctl action-items watch` reports the real change when a save truncates the file first** (`engine/scout/action_items/watch.py`). `Path.write_text` and most editors truncate the file, then write it. When the watcher handled the truncate's event before the write landed, it read an empty file. It then printed every item as removed, re-added them all on the next event, and never reported the actual change (a checkbox flip, say). Seen on macOS CI under load. The watcher now re-reads after a 50 ms pause until two reads agree before it diffs. An empty read of a file that had content counts as unfinished until about 0.5 s of re-reads, so a file really emptied still reports its removals. Atomic saves, which write a temp file and rename it over the target, are now seen too: a move onto the target or a create of it triggers a diff, where before only in-place modifies did.
- **A new vault is a git repo** (#433; `engine/scout/scripts/bootstrap.py`). Nothing ever ran `git init`: the git-setup phase only sets the identity, so a fresh vault (on Linux, and on macOS too) stayed a plain folder, run commits failed, and the kb-lint pre-commit hook was skipped. `scoutctl bootstrap install` now initializes the vault and makes one initial commit, then installs the hook in the same run. The commit uses the run's own identity (`<Instance> Bot` and your email, set in the vault's `.git/config`), so it works on a host with no global git identity, and it is never signed or hooked. `bootstrap upgrade` does the same for a vault that is not a repo yet, so the next update repairs a vault installed without one. An existing repo is never touched. With no `git` on the host the install warns and carries on.
- **Phase shell commands run on Linux** (#434; `phases/connectors/github.md`, `phases/core/git-setup.md`, `commands/scout-meta-review.md`). The GitHub scan's five time filters used BSD-only `date -v-NH`, which fails on GNU/Linux and left the filter empty. They now use a `python3 -c` one-liner. Three of them also put a `Z` (UTC) on a local time, which moved the window by the UTC offset on macOS too; all five are now real UTC instants. The timestamp-conversion rule's example used GNU-only `date -d`, and `/scout-meta-review` read log dates with BSD-first `stat -f`, which on Linux printed filesystem details instead; both use `python3 -c` now. A new test fails on BSD-only or GNU-only `date`, `sed -i` and `stat -f` usage in phases, commands, skills, templates and scripts.

### Security
- **The action-items HTML dashboard escapes link URLs and only links web and mail addresses** (#435; `engine/scout/action_items/render.py`, `templates/action-items/render.py`). A markdown link's URL went into `href="…"` unescaped, so a `"` could break out of the attribute, and a `javascript:` link stayed clickable. Action items are written from Slack, mail, GitHub and Linear text, so that URL can come from someone else. Both renderers now escape the URL for the attribute and make a link only for `http`, `https` and `mailto`. Any other scheme (including mixed-case, whitespace-split and entity-encoded `javascript:`, `data:`, `file:`, `obsidian:`) and any URL without a scheme renders as the link's label in plain text. Existing vaults pick up the template change with `/scout-update`.

## [0.18.0] - 2026-10-13

### Added
- **Engines installed without Scout.app update themselves** (#360; `engine/scout/scripts/self_update_run.py`, `engine/scout/scripts/self_update.py`, `engine/scout/update_outcomes.py`, `engine/scout/health.py`, `engine/scout/cli.py`, `templates/scripts/heartbeat.sh.tmpl`). The new `scoutctl self-update run` updates an engine installed with `install.sh` or Claude Code to the newest stable release. It does this only when `auto_update.enabled` is `true`, and only once the release's GitHub release `vX.Y.Z` is published (not a draft, not a prerelease) and at least `auto_update.soak_hours` old (default 24). The heartbeat starts it at most once a day, detached, preferring the off-peak hours. Outside them it runs only when the last check is more than 36 h old. It puts the attempt off while a session holds the vault lock or a slot is due within 45 minutes. It fetches the plugin through Claude Code and builds the new engine's venv in the new plugin folder, without the vault lock. It then hands the vault to the new engine's `bootstrap auto`, which takes the lock and re-points the jobs, shim and engine pointer. A failure before that step leaves the old engine running untouched. A failure at or after it is reported and never rolled back: run `scoutctl bootstrap upgrade`. A pending `parser.py` merge or a red install doctor holds the update. Brain-file merges never hold it; they are parked as in any upgrade. A failed version is retried after 24 h, and given up after 3 failures until a newer release appears or you run `scoutctl self-update run --force`. `--dry-run` says what would happen. Engines Scout.app manages are never touched, since the app updates them. `dev` checkouts are never updated, only checked. Each attempt is one row in `.scout-logs/update-outcomes.jsonl`, and `scoutctl health` reports from it: `update.failed` (red, pushed), `update.held` (yellow: held, or put off for more than 72 h), `update.sidecars` (yellow: files left to merge) and `update.behind` (a note: a release more than 14 days old not yet applied, or a dev checkout behind the latest release). You get one push for an update that left files to merge, and one for the first update a vault receives.
  **Behaviour change:** a vault not managed by Scout.app whose `scout-config.yaml` already has `auto_update.enabled: true` (`/scout-setup` asked this question for a long time, and nothing acted on the answer until now) starts updating itself once the heartbeat runs the new template. Turn it off with `scoutctl config set-auto-update --disabled`. Existing vaults pick up the heartbeat change with `/scout-update`.
  **Getting 0.18.0:** an engine on 0.17.x has no updater yet, so it does not update itself to 0.18.0. Run `/scout-update` once (or `scoutctl bootstrap upgrade`) to reach 0.18.0. From then on each stable release installs itself, so the first automatic update is 0.18.0 → 0.18.1.
- **`scoutctl setup` asks whether to keep Scout up to date** (#360; `engine/scout/setup_wizard.py`, `engine/scout/cli.py`). A first install whose engine came from `install.sh` or Claude Code asks "Keep Scout up to date automatically?". Yes is the default, and `--yes` turns it on. `--auto-update` / `--no-auto-update` answer it without the prompt. `scoutctl bootstrap auto` gains the same flags and records the answer on install and on upgrade; omitting them leaves the vault's setting alone. `/scout-setup`'s question now describes what actually happens. The packaged defaults gain `auto_update.soak_hours: 24`. `scoutctl health` adds an `update.last` note ("Updates automatically. Last checked …"), which Scout.app shows for engines that update themselves.

### Fixed
- **The `AUTO_UPDATE_ENABLED` template variable follows the vault** (`engine/scout/scripts/bootstrap.py`). It read a connector input that nothing sets, so it always rendered `false`. It now reads this run's `--auto-update` flag, then the vault's `auto_update.enabled`, then the packaged default.

## [0.17.4] - 2026-10-13

### Added
- **Scheduled runs can use a long-lived Claude token, so they survive the interactive login's expiry** (#267, run-health P6; `engine/scout/claude_auth.py`, `engine/scout/cli.py`, `engine/scout/setup_wizard.py`, `engine/scout/scripts/bootstrap_doctor.py`, `engine/scout/health.py`, `templates/scripts/claude-with-retry.sh.tmpl`). An expired `claude` login stopped every scheduled run until someone signed in again.
  - **`scoutctl auth setup-token`** runs `claude setup-token`, then reads back the one-year token it prints, with input hidden. Both stores are outside the vault and never committed:
    - On macOS it goes in the login Keychain as the generic-password item `scout-claude-oauth-token` (account: you). It is written through `security -i` on stdin, never on a command line.
    - Elsewhere it goes in `~/.config/scout/claude-oauth-token`, mode 0600 in a 0700 directory.
  - On a host with no browser, `--stdin` takes a token made elsewhere. `scoutctl auth status [--json]` and `scoutctl auth clear` complete the set. No command prints the token.
  - **The run wrapper exports it.** Every runner launches Claude through `scripts/claude-with-retry.sh`, which now exports the stored token as `CLAUDE_CODE_OAUTH_TOKEN` when the variable is unset. If the Keychain is locked, or refuses the read, the run uses the interactive login and says so in its log. Each run records its sign-in mode (never the token) in `.scout-logs/.claude-sign-in.json`. The doctor notes that mode, and run health raises a yellow `auth.token_unreadable` when a stored token couldn't be read.
  - **A rejected token gets its own fix.** `claude auth login` can't help once a token is exported, so the wrapper's auth banner and desktop alert, and run health's `auth.expired`, name `scoutctl auth setup-token` instead.
  - **Expiry is tracked from the date stored.** The CLI can't tell when a token expires, so a sibling `claude-oauth-token.meta.json` records only when the token was stored. A token in its last 30 days, or past them, is a yellow `auth.token_expiring` finding in `scoutctl health` and a doctor warning.
  - **The doctor reports the sign-in mode** as a note: the interactive login, or the token with its store and estimated expiry. It warns on a token file readable by others, and on a stored token whose vault runner predates the export (fix: `/scout-update`).
  - **`scoutctl setup` offers it on a fresh install.** Interactive only, default no, and skipped when a token is already stored. Under `--yes` it prints how to do it later. App-managed engines are never offered it (spec Q6).
  - Existing vaults pick up the wrapper change with `/scout-update`.

### Fixed
- **An eval run writes the day it was rendered for, not the real date** (`engine/scout/config.py`, `engine/scout/action_items/materialize.py`). The eval harness renders a scenario for one day (`eval.sh run --today`, and the unit tests' fixed Monday) and pins it as `SCOUT_EVAL_TODAY`, but only its stubs read the variable. The runner's carry-forward step (`scoutctl action-items materialize`) used the clock, so any day other than the real one carried the fixture into the real date's file, and every check scored a file the session never wrote. Three `test_eval_runner.py` tests began failing on 2026-10-13, the day after their pinned Monday. `scout.config.today()`, the one day boundary every daily-file path goes through, now returns the pinned day when `SCOUT_EVAL_TODAY` is set, and refuses a value that isn't `YYYY-MM-DD`. `materialize` honours it too, but falls back to the clock on a bad value, since that step must never block a run. Real runs never set the variable: no template changed, and with it unset every path reads the clock exactly as before. Session-side phase text that computes today with shell `date` (`phases/core/git-setup.md`, `phases/core/action-items.md`) still reads the clock, which only matters for `--today` runs on a day other than today.
- **"Not logged in" counts as an auth failure** (#267 comment; `templates/scripts/claude-with-retry.sh.tmpl`, `templates/scripts/run-outcome.sh.tmpl`, `engine/scout/health.py`). A Mac set up again comes up logged out rather than expired. Each scheduled run then died in seconds on `Not logged in · Please run /login`, which matched none of the auth patterns. So the runs were recorded as `unknown` and no auth alert fired. The three shared auth regexes now match it at line start. Existing vaults pick this up with `/scout-update`.
- **A run that finds the session lock busy waits for it, and a waiter skips work its holder just did** (#218; new `templates/scripts/scout-lock.sh.tmpl`, `templates/run-scout.sh.tmpl`, `templates/run-dreaming.sh.tmpl`, `templates/run-research.sh.tmpl`, `templates/scripts/run-outcome.sh.tmpl`, `engine/scout/scripts/bootstrap.py`). The three runners carried three copies of the lock code, and a run that found the lock held exited at once, so a slot the scheduler had already stamped as fired never ran. The lock now lives in one file, `scripts/scout-lock.sh`, which each runner sources. A busy lock is polled every 30 s for up to 30 min (`SCOUT_LOCK_WAIT_SECS`, `SCOUT_LOCK_POLL_SECS`). A holder that crashes or wedges during the wait is still recovered, as before. A wait that runs out records `skipped_lock`. Once it has the lock, a run looks in the run ledger for an `ok` run of its own kind that finished in the last hour (`SCOUT_REDUNDANT_WINDOW_MIN`, default 60). A dreaming or research run that waited, behind a run of its kind that finished during that wait, would repeat the same phases over the same vault, so it records `skipped_redundant` and stops. Every other case logs a note and runs: a waiter behind a failed holder (that is the recovery the wait exists for), a different kind, a `run-scout.sh` run (briefing and consolidation are different work), and a back-to-back run that never waited (it is sometimes the only reader of the last run's blind spot). `SCOUT_REDUNDANT_WAIT=off|warn|enforce` overrides this. Ledger rows now carry `runner` (`scout`, `dreaming` or `research`); only rows that carry it count as a witness. A runner whose `scripts/scout-lock.sh` is missing fails loudly instead of running unlocked. Existing vaults pick this up with `/scout-update`, which renders the runners and `scout-lock.sh` together.
- **A scheduled run holds an idle-sleep assertion, through the retry backoff too** (#210; `templates/scripts/claude-with-retry.sh.tmpl`). Nothing stopped an unattended Mac from idle-sleeping mid-run, which killed the streaming response and failed the run with what read as an API error. Each attempt and each backoff `sleep` now runs under `caffeinate -i -m -s` on macOS, or `systemd-inhibit --what=idle:sleep` on Linux when it can take the lock (cron often can't, and then nothing changes). The backoff matters most: the wrapper is deliberately idle there. `SCOUT_NO_CAFFEINATE=1` turns it off. The log now also says how long a backoff actually took. A closed lid still sleeps the machine.
- **The run ledger says what landed in each run's window, measured** (#237; `templates/scripts/run-outcome.sh.tmpl`, `engine/scout/health.py`). A run that committed and was then killed (by a sleeping host, say) was indistinguishable from one that produced nothing. Each row now carries `commits_in_window` and `newest_commit`, counted with `git log` over the run's start and finish. The start is checked first: `git log --since` silently reads a bad or pre-2001 bound as "now" and answers 0, so an implausible start, or a vault with no git history, records `null`, never `0`. The `runs.failing` finding now adds "N commit(s) in that run's window (newest `abc1234`)" or "No commits in that run's window", and nothing when the count is `null`. It says "in that run's window", never "by this run": a window is observable, authorship isn't. Rows also carry `trigger` (`schedule`, `heartbeat` or `manual`, the last from the `SCOUT_TRIGGER=heartbeat` the heartbeat sets since #231).
- **A weekly usage limit pauses Scout until the date it names, and run health says so instead of going red** (#424; `engine/scout/health.py`, `engine/scout/health_notify.py`). Claude Code's weekly limit names a date: "You've hit your weekly limit · resets Oct 15 at 2pm (Europe/Prague)". The reset parser read only a time or a weekday, so no `resets_at` was recorded. The budget gate then backed off for two hours only, every scheduled slot until the reset started a session that failed in seconds as `rate_limited`, `scoutctl health` reported a red `runs.failing` for days, and the notifier re-alerted every day. #426 (thanks @jay23606) taught `scoutctl budget resets-at` to read the date. With it read, the gate holds every slot until the reset and records each as `skipped_budget`, and no session starts. Run health now reports one yellow `runs.paused` ("Claude usage limit — runs paused until <time>") in place of `runs.failing` while a rate-limited run's reset is still ahead, however many runs failed on the limit first. A lane that was inside its dark budget when the limit hit isn't reported dark while the pause lasts. When the report leaves red because of the pause, the notifier's one push says "runs paused" with the resume time instead of "runs recovered". The fix is engine-only: the vault's scripts are unchanged.

## [0.17.3] - 2026-10-12

### Fixed
- **Every heartbeat cadence knob can be set in `scout-config.yaml`** (#231; `engine/scout/scripts/heartbeat.py`, `engine/scout/scripts/bootstrap_doctor.py`, `engine/scout/defaults/scout-config.yaml`). The heartbeat checks every 30 minutes whether to launch an extra dreaming or research run. Of its six settings, only the two off-peak hours were read from config. The four that decide how often it launches (`min_gap_minutes`, `off_peak_min_gap_minutes`, `dreaming_signal_hours`, `research_min_gap_hours`) could only be changed in engine source, and a key written for them was dropped without a word. They are now read from a nested `heartbeat:` block; the flat top-level spellings work too, and the nested value wins when both are set. A value out of range or not a whole number keeps that knob's default, and an unknown key under `heartbeat:` is ignored. Both are no longer silent: each is logged to `heartbeat.log` on every tick and reported as a `bootstrap doctor` warning. Uncommitted vault edits, the second reason the heartbeat launches, no longer count when they are only Scout's own `.scout-state/`, `.scout-logs/` or `.scout-cache/` files, and the new `heartbeat.dirty_tree_triggers: false` turns that reason off. Each launch line now names its reason (`trigger=signal_hours`, `trigger=dirty_tree` or both). The off-peak window is read in the configured timezone, the same zone the log stamps use. Heartbeat launches set `SCOUT_TRIGGER=heartbeat` for the run ledger. Defaults are unchanged, so a vault that sets nothing behaves as before. The README's troubleshooting section documents the block. Nothing to re-render: the heartbeat's launchd job still fires every 30 minutes and reads the config on each tick.
- **A review request sent to one of your teams no longer goes missing from the action items** (#404; `engine/scout/action_items/review_requests.py`, `engine/scout/action_items/cli.py`, `engine/scout/scripts/pre_session_data.py`, `phases/connectors/github.md`, `phases/core/action-items.md`, `phases/core/00-run-modes.md`). The agent-behaviour eval missed a team-only request in 3 of 5 runs: either the session skipped GitHub's review-request search, or it ran the search and never classified that PR. The new `scoutctl action-items check-review-requests` lists every review request the runner pre-fetched into `.scout-cache/session-context.json` that today's action items don't account for. A request is accounted for when an item names its `owner/repo#N` or URL, when a run-notes line says `Skipped review request owner/repo#N — <reason>`, or when you dismissed its link. The command exits 0 when everything is accounted for, 1 with a list, and 2 when it can't check. `--json` gives the same result as data. ### Fixed
- **Two waiters can no longer both take the vault lock after a crash** (`engine/scout/scripts/bootstrap_lock.py`). Stale-lock recovery read the dead holder's PID, then unlinked the path. A second waiter acting on the same dead PID could delete the live lock the first had just taken and then win its own, so both went on to write the vault. Recovery now runs behind a short-lived `O_EXCL` `.scout-session.lock.takeover` guard and re-reads the PID while holding it; a guard left by a process that died mid-recovery is cleared after 30 s. `release_lock` and `remove_stale_lock` no longer delete a lock whose contents don't parse, which is a competitor between its create and its PID write. Affects `bootstrap install|upgrade|resolve` and `connectors custom add|remove` (#322).
- **A runner can no longer share the vault lock with `scoutctl` or another runner** (`templates/run-scout.sh.tmpl`, `templates/run-dreaming.sh.tmpl`, `templates/run-research.sh.tmpl`). The runners took `.scout-logs/.scout-session.lock` with their own shell sequence: check the file, remove a stale one, then `echo $$ >` over the path. A runner could overwrite a lock created after its check, including one `scoutctl` had just taken with `O_EXCL`. Two runners recovering the same crashed holder could each delete the lock the other had just taken. An empty lock, left by a competitor between its create and its PID write, counted as stale. And the EXIT trap deleted whatever lock it found, even another holder's. The runners now follow `bootstrap_lock.py`'s protocol. They create the lock atomically with noclobber (`O_EXCL`). They remove a crashed holder's lock, or reap a wedged one past `SCOUT_LOCK_MAX_AGE_SECS`, only under the `.scout-session.lock.takeover` guard and only if the PID re-read under it is unchanged, and they clear a guard after 30 s. They treat an empty or unparseable lock as busy, and their EXIT trap removes the lock only while it still holds the runner's own PID. In a stress run of 6 runners racing a crashed holder's lock for 150 rounds, the old block let two sessions run at once 467 times and the new one 0. The log lines and the `failures.log` reap record are unchanged. Existing vaults pick this up with `/scout-update` (#331).
- **The 98% engine coverage floor now fails CI every time it is missed** (`engine/pyproject.toml`). The exit code rounded the total to whole percent, so 97.65% passed under a FAIL line; `precision = 2` fixes that, and new tests take the total to 98.33%.
- **The launcher skips a monorepo marketplace clone's root `.venv`** (`engine/bin/scoutctl`). Fired from Claude Code's `cache/` copy, the launcher cross-jumps to the `marketplaces/` clone and probed that clone's root `.venv` before `plugin/.venv`. In a Raven-Scout/Scout clone (`.claude-plugin/marketplace.json` at the root, the plugin at `plugin/`), a root venv is a stale editable install from before the pull, so when it still imported `scout.cli` it shadowed the real engine. - **Brain-file merges no longer conflict over a final newline** (`engine/scout/scripts/three_way_merge.py`) — `git merge-file` reported a conflict when only one side ended in a newline, e.g. after an editor saved `SKILL.md`. All three merge inputs are now newline-terminated before merging; assembled files are byte-for-byte unchanged.

### Fixed
- **A cached interpreter that can't import the engine no longer breaks every `scoutctl` call** (`engine/bin/scoutctl`). When a `~/scout-plugin` checkout was pulled into the monorepo layout, `engine/` moved to `plugin/engine/`. The old `.venv/bin/python` still ran but died with `No module named scout.cli`, so every call failed, every Scout.app write among them. - **A pending brain-file sidecar no longer blocks the next upgrade** (`engine/scout/scripts/brain_merge.py`, `engine/scout/scripts/bootstrap.py`). A `SKILL.md`/`DREAMING.md`/`RESEARCH.md.proposed-merge` left from an earlier upgrade used to make every later `scoutctl bootstrap upgrade` refuse before any stage ran. Scripts, runners, jobs and the version stamp all stayed on the old plugin, and an unattended auto-update stalled until someone resolved the sidecar by hand. Now only that file is skipped: its live file, its snapshot and the half-resolved sidecar are left exactly as they are, and every other stage runs. The skip is reported as `UpgradeResult.skipped` (and `skipped` in the `--json` result Scout.app decodes), as a `skipped (sidecar pending):` line from the CLI, as a doctor warning, and by `/scout-update`, which no longer refuses on it. `scoutctl bootstrap auto` no longer refuses on it either. A pending `parser.py` sidecar an older engine left still blocks.
- **A plugin change to a brain file reaches a vault that never edited it.** When the live file still matched its snapshot, any change to the plugin's assembly went to a sidecar instead of being applied, so every release left a sidecar on a vault that had done nothing. That rule guarded the M3 incident, where `migrate-legacy` seeds the snapshot from the live file and a match proves nothing. The guard is now provenance. `.scout-state/last-assembled/provenance.json` records the hash of each snapshot the engine writes, and `migrate-legacy` marks its snapshots as seeded. The live file is replaced or merged only over a snapshot the plugin is known to have written. A vault from before this release falls back, once, to the header every bootstrap assembly starts with, but the header alone never licenses a fast-forward: a hand-grown brain can start with it too, so where live still matches such a snapshot (the M3 signature) the change is proposed, once, and adopting it converges. Anything else gets the plugin's version as a proposal in the sidecar. This also closes a second path to the M3 loss: a 3-way merge against a seeded snapshot could come out "clean" and delete the legacy brain. A proposal adopted verbatim (`mv X.md.proposed-merge X.md`) converges on the next upgrade; anything else converges through `bootstrap resolve`. When the header fallback vouches for a merge into live, the file from before the merge is parked as `.scout-state/drift/X.md.vault` (reported as a backup and a doctor note; `scoutctl bootstrap drift --resolve X.md` dismisses it). Provenance is written after each file, so an upgrade that fails part-way keeps the records it made. A `provenance.json` that can't be parsed fails closed: it is set aside as `.corrupt` rather than overwritten, and every brain file is proposed, never merged or replaced, until it is recorded again. A live brain file that still has `<<<<<<<`/`>>>>>>>` lines (a conflict sidecar moved into place unfinished) is held: nothing is merged into it, its snapshot doesn't advance, and it is reported as `conflict_markers` (`held (conflict markers):` from the CLI) and as a doctor warning. The doctor suggests `mv`-ing a sidecar into place only when it has conflict markers; a marker-free proposal is the plugin's whole version, and moving it would replace the vault's brain. `scoutctl phases backport` is unchanged, because the snapshot still advances only once the live file has absorbed the assembly. - **The dreaming brain no longer instructs its own commit steps to run bare `git add -A`** (`phases/modes/feedback-processing.md`, `phases/modes/kb-deep-work.md`, `phases/modes/wishlist.md`) — all four dreaming commit steps (Phase-1 feedback, applied-proposal, Phase-2 KB deep work, Phase-3 wishlist) told the agent to stage the **entire working tree**. That has now happened six times in the vault; on 2026-10-02 an evening-consolidation's `-A` swallowed a dreaming run's in-progress KB section **mid-rename**, committing a duplicate section heading under the consolidation's message — the first recurrence to produce a visible artifact defect rather than only a mangled provenance trail. ### Fixed
- **An upgrade never silently loses a vault's edit to a plugin-owned file** (`engine/scout/scripts/bootstrap.py`, `engine/scout/scripts/vault_drift.py`). Before this, an upgrade handled a vault's own edits like this:
  - Cat-1 files (scripts, hooks, `render.py`, `recurring-task-status.py`) were overwritten with no backup and no warning.
  - Runners were replaced after being copied to `run-*.sh.bak.<date>`, so the live runner lost the edit.
  - A `parser.py` conflict wrote a sidecar that made the *next* upgrade refuse to run, which would stall an unattended auto-update.

  Every plugin-owned file now follows one policy. The plugin's last render is recorded in `.scout-state/last-rendered/`, so an upgrade can tell a vault edit from a template change:
  - An unedited file takes the plugin's update.
  - An edit the plugin didn't touch is kept.
  - When both changed, the edit is 3-way merged, and a clean merge is applied.
  - On a conflict the vault's version keeps running. The update is parked at `.scout-state/drift/<file>.plugin`, with a conflict-marked `.merge` draft, and every later upgrade retries the merge. Nothing parked there blocks an upgrade.

  `UpgradeResult.vault_edits` reports each kept, merged, conflicting or replaced file, and `bootstrap upgrade` prints one line per edit. One bad file can't stop the stage: a byte that isn't UTF-8 round-trips unchanged, and an unreadable or locked file is reported as `error` and left untouched while the rest upgrade. The bases in `last-rendered/` are tracked by the vault's git, so a re-clone keeps them. A pending conflict turns `bootstrap doctor` yellow. Kept edits and parked copies show as doctor *notes* (new `DoctorReport.notes`), which leave the severity alone. Only the assembled `SKILL`/`DREAMING`/`RESEARCH.md` sidecars still block an upgrade. ### Fixed
- **`release.sh --finalize` could never succeed** (`scripts/release.sh`) — the "is this version on origin/main yet?" guard piped `git show origin/main:CHANGELOG.md` into `grep -q`. `grep -q` exits the instant it matches, closing the pipe while `git show` is still writing, so `git show` dies of SIGPIPE with status 141; `set -euo pipefail` then makes 141 the *pipeline's* status, and `!` inverts that failure into the error branch. Both outcomes therefore printed `origin/main CHANGELOG has no [X.Y.Z] section — merge the release PR first`: no match → exit 1 (right answer, wrong reason), match → exit 141 (wrong answer). The bug is position-dependent — a match late in the file lets `git show` finish inside the pipe buffer — so it fires hardest on exactly the case that matters, a freshly promoted section at the top of the file. v0.9.0 had to be tagged by hand as a result. The guard now reads the blob into a variable and matches it with a herestring, so there is no pipeline for `pipefail` to poison. (#225)
- **Transient API failures skipped their retry on a chatty run** (`templates/scripts/claude-with-retry.sh.tmpl`) — same SIGPIPE-under-`pipefail` shape: `tail -50 "$LOG_FILE" | grep -qE "$TRANSIENT_PATTERNS"` returns 141 rather than 0 when the match lands early and the 50-line tail outgrows the pipe buffer, so `! …` reclassified a retryable error as "not classified as transient — no retry", defeating the wrapper. The tail is now snapshotted once and matched from a variable (which also drops a duplicate `tail`). (#225)
- **Hardened the first-match extraction in rate-limit detection** (`templates/scripts/rate-limit-detect.sh.tmpl`) — `echo "$MATCHES" | head -1 | cut` has the same unbounded-writer/early-reader shape; a 141 there would propagate through `set -e` and be read by the runner as "no rate limit detected". Not reproduced in practice (bash's builtin `echo` usually survives the EPIPE), so this is a latent hardening rather than an observed failure. (#225)

## [0.7.1] - 2026-06-19


### Added
- **Per-file Wishlist & Research Queue (#144)** — the vault's Wishlist and Research Queue move from single markdown files to per-file directories (`docs/wishlist/`, `knowledge-base/research-queue/`), one file per item, so items are easier to edit, track, and reference individually. An **idempotent migration runs automatically during `/scout-update`**: it writes every existing item to the new per-file layout *before* removing the legacy files (no content loss; safe to re-run), and the heartbeat detects open research items in the new layout with a fallback to the legacy file during the transition.
- **`scoutctl phases backport`** — reverse-maps vault brain-file edits (`SKILL`/`DREAMING`/`RESEARCH.md`) back into their source `phases/` fragments, so a future `/scout-update` re-render carries them forward instead of sidecaring (closes the manual half of the back-port gap). Diffs each brain file against its `.scout-state/last-assembled/` snapshot, locates each divergence in its fragment by anchor matching, conservatively re-templatizes (only long/unique vars auto-reverse; short ones like the instance/user name are flagged, never auto-written — so instance data can't leak into the engine), and **only auto-writes pure insertions that round-trip** (re-assembly reproduces the vault line); modified lines (diff `replace`) are downgraded to needs-review so the old text is never left behind. Default is a read-only report (`--apply` writes; `--kind`, `--vault` flags). Never commits/pushes/opens a PR. New module `scout.scripts.phase_backport` (pure, unit-tested) + `phases` CLI sub-app. Design: `docs/superpowers/specs/2026-06-16-scoutctl-phases-backport-design.md`.
- **Engine back-port reminder** (`phases/modes/feedback-processing.md`, Step 1e) — after a run applies a `SKILL`/`DREAMING`/`RESEARCH` proposal, it surfaces a standing reminder (in the wrap notification + as a carried action item) that the engine back-port is owed until its PR merges, pointing at `scoutctl phases backport`. Explicitly **operator-triggered only — never auto-run** (it writes the shared engine). Closes the "applied edits silently never reach `phases/`" loop with a nudge instead of automation.

### Documentation
- **Budget-skip troubleshooting** (`README.md`) — guidance for diagnosing sessions skipped by the budget gate (#143).

## [0.7.0] - 2026-06-17


### Added
- **User-extensible connector probes (#97)** — custom connector probes now live in `~/Scout/connector-probes.local.yaml` (same schema as the shipped registry), merged over the shipped probes with the overlay winning on key collision. The overlay lives in your vault and survives plugin updates — the previous behavior silently wiped custom probes on every update. New `scoutctl connectors probe-registry [--json]` emits the merged registry, and `/scout-setup` now reads it instead of the raw shipped file. A malformed overlay fails loudly (naming the file), never silently dropped.
- **`scoutctl action-items mark-done --undo`** — reopens a completed task (the reopen path the scout-app UI invokes; previously the only action-item operation with no working path). Supports `--by-id` and `--subject` like the other mutators (#116).
- **DM legibility rule** (`phases/connectors/slack.md`) — wrap DMs must never surface a bare internal `#SHORTCODE` tag (expand inline or drop) and must include a clickable link to the day's action-items file (Obsidian URI / `file://` path). Presentation-layer only; the file-side tag-keying machinery is untouched.
- **No-unverified-negatives discipline** (`phases/core/action-items.md`) — before asserting a negative completion-state ("not done", "still your move", "not created") on a connector-observable item, the run must query that connector or mark the claim `[unverified — not queried this run]`.
- **Repo-creation verification** (`phases/connectors/github.md`) — the GitHub scan now lists recently-created/updated repos via `gh repo list`, since a brand-new repo has no PR and is invisible to the PR scans; verify "stand up repo X" items this way before carrying them as not-done.
- **Batch-comment triage mode** (`phases/modes/kb-deep-work.md` Step 2-pre, with a pointer in `phases/core/action-items.md`) — when an inline-comment sweep finds more than N=5 unprocessed `//==<<` markers, switch from resolve-each to inventory/categorize/route into a dated `comment-triage-YYYY-MM-DD.md` index, leaving markers in place and surfacing the index.
- **Research priority preemption** (`phases/research/research-targets.md`) — target selection runs 🔴/`START IMMEDIATELY`/user-directed queue items before the staleness-rotation or opportunistic pick, and surfaces a >1-run-open 🔴 directive as overdue.
- **MIT License** (#135).

### Changed
- **Audits remediate or hand off, never just report** (`phases/modes/kb-deep-work.md` Step 2-ontology) — after producing findings, audits split them `auto-remediable` (fix in-run or hand to the next run as a must-action queue) vs `backlog` (leave; don't auto-create), and the notification states what was *fixed*, not only what's wrong.

### Fixed
- **Concurrent bootstrap could double-acquire the pipeline lock** — `acquire_lock`'s stale-lock pre-check removed the empty lock a racing winner leaves between its `O_EXCL` create and its PID write, letting two callers both "win". Stale recovery now happens only on the create conflict and only for a confirmed-dead PID (#36 residual).
- **`render.parse()` now strips the leading `[#TAG]` prefix** from `subject`/`plain_subject`, matching the Swift reference parser so `--subject` matching and click-to-copy needles agree across scout-plugin and scout-app (#114).
- **`mark-done`/reopen accept uppercase `[X]`** — a task completed as `[X]` is now reopenable, not just `[x]` (#56).
- **launchd plist re-install is idempotent** — `bootout` before `bootstrap` so `/scout-update` no longer emits `Bootstrap failed: 5: Input/output error` and leaves the old job loaded (#23, #48).
- **`bootstrap upgrade` can't hang forever** — `git merge-file` runs with a 30s timeout (#47).
- **Same-day runner backups are never clobbered** — a second `/scout-update` the same day writes `<name>.bak.<DATE>-1/-2/…` instead of overwriting the first run's backup and losing that hand-edit (#62).
- **`bootstrap upgrade` survives a non-UTF-8 or malformed `scout-config.yaml`** — read as UTF-8 with a typed error (exit 10) instead of an internal-error crash (#45).
- **A customized/missing KB schema no longer crashes** the `KnowledgeGraph` constructor (and the TUI) — typed `KBSchemaError`, and `validate()` tolerates entity types with no `properties:` key (#46).
- **TUI session spawner** — action-item titles can no longer break the AppleScript literal or inject shell (correct escaping + sanitized session name), and `osascript` runs off the Textual event loop so the UI doesn't freeze (#52).
- **KB freshness dates are DST-correct and discovery can't hang** — `parse_date` returns timezone-aware values, and KB-file discovery no longer follows symlinks (a symlink loop previously hung session startup) (#53).
- **Malformed/unreadable connectors YAML** surfaces a typed `ConfigError` instead of a raw `OSError` traceback (#43).
- **Action-item prefix backfill is corruption-safe** — it parses the same bytes it edits (closing a TOCTOU window) and registers each prefix as it writes, so a mid-run failure can't desync the id-map and re-mint live prefixes (#41, #42).
- **Plugin-side parser-corpus checksum guard** keeps the cross-language contract corpus byte-identical with scout-app (#115); the test suite is now hermetic against a live `~/Scout` vault.

### Performance
- **No per-file Python cold starts in the KB pre-filter** — `kb-pre-filter` now delegates to `scoutctl hook kb-pre-filter` instead of spawning a `python3 -c` interpreter per KB file via its date-parse fallback; this was the last per-session script still shelling out to Python (#74).

## [0.6.0] - 2026-06-07

### Added
- **Variable-length `[#TAG]` action-item IDs** — the recognition grammar now accepts 2–8 `[A-Z0-9]` tags containing at least one letter (e.g. `[#PLANREV]`, `[#XI7391]`, `[#NTX]`), not just 4-char Crockford. Pure-numeric `[#123]` stays reserved for GitHub issue refs. The generation prompt now encourages meaningful mnemonics, with `action-items new-prefix` as the random fallback. Fixes the real-vault gap where scout-app fell back to brittle `--subject` matching on the most-referenced lines (scout-app#10, #117).
- **Deterministic post-session prefix backfill** — briefing/consolidation runners run `action-items backfill-prefixes` at session end, so every open task carries a stable `[#TAG]` independent of prompt compliance (#113).
- **Cross-language parser contract test** — a golden corpus + SHA-256 checksum guard proving the Python (scout-plugin) and Swift (scout-app) parsers agree, seeded with the historically-broken lines (#113, #117).

### Changed
- **`action-items --by-id` is ambiguity-aware** — errors when a tag is shared by multiple open tasks instead of silently acting on the first (reusable semantic tags can collide; #117).
- **`new_short_prefix` guarantees a letter** — minted Crockford-4 prefixes always contain at least one letter, so every mint is recognized by the widened grammar (#117).
