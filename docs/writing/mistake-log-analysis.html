Field notes · Data through 22 November 2026

297 logged mistakes from an unattended agent, classified

Scout has run on its own, on my Mac, since April. Every mistake it was caught making got a numbered write-up. I classified all of them. Who catches the mistakes changed a lot. Whether there are fewer of them, I can't tell you. And a third of the fixes didn't hold.

Raven Scout · the developer of Scout · November 2026

The short version

  1. Making things up was a minority cause. About a fifth of the mistakes (22%) were the model inventing or over-reading something. The biggest cause (36%) was the instructions: a rule that was missing, wrong, or there and not followed.
  2. Who catches the mistakes is what changed. In April I caught 91% of them myself. By October the agent's own review runs caught 83%.
  3. That is not the same as making fewer mistakes. I have no clean way to count those, and the share of entries that repeat an earlier one stayed flat at about one in ten.
  4. A third of fixes didn't hold. 109 entries had a fix shipped; 39 of them (36%) happened again afterwards.
  5. As the system grew, the failures moved into my own code. In October and November, 44% of entries were bugs in Scout's scripts, not in the model's thinking.
  6. The worst failures were silent. The most expensive ones were the system reporting success while doing nothing.

01What Scout is, and why I'm publishing this

Scout is a plugin for Claude Code that runs unattended on a schedule. On a weekday it starts five sessions between morning and evening. Each one reads my Slack, email, calendar, Linear, GitHub and meeting notes, and updates two things in a git repository on my Mac: a daily action list, and a Markdown knowledge base about my work. In the evening, separate sessions (I call them dreaming) go back over the day's output looking for mistakes. Research sessions, overnight and mid-afternoon, read outward. Nobody watches any of this live. I read the list and the briefing it sends me, and I reply when something is wrong.

That makes the mistake log the most honest thing the project has. A demo shows the good days. The log shows every day something went wrong badly enough that someone wrote it down. If you're deciding whether to trust an agent like this with your work, or building one, the log is the thing worth reading, so here it is, with the parts that don't flatter the project kept in.

02How the log works

When a mistake is caught, the session that catches it writes an entry. Each entry gets a number and records what happened, the root cause as the agent sees it, what was changed to fix it (if anything), and a status. A mistake is caught in one of two ways:

  • I catch it. I reply to a briefing in Slack, leave a comment next to an item in the app, or say so in a working session.
  • The agent catches it. A dreaming or consolidation run, a check script, a test, or a session that notices it on its own while doing something else.

Three things about the log matter for reading the numbers.

An entry is a failure mode, not a single slip. One entry can cover several occurrences of the same thing: the entries that state a count add up to 489 occurrences across 287 entries. When the same failure comes back, it's often recorded as a new instance inside the existing entry; sometimes it gets a new number that names the older one.

It is not a census. An entry exists when someone thought a failure was worth writing up. Small slips that got fixed in place often didn't get one. How thorough the logging was also changed over time, which comes up again below.

The agent writes the entries. Including the root-cause diagnosis. That's the biggest single bias in this dataset, and I come back to it in the caveats.

The data here covers every entry from the first, on 10 April 2026, to the last one logged before I pulled the data, on 22 November 2026. That's 297 entries: 291 numbered ones (numbers run to 294, with three missing from the sequence) and 6 unnumbered drafts.

03How I classified it, and how I checked

I wrote a fixed rubric and had Claude read every entry against it, one entry at a time, reading the full write-up rather than the title. The rubric's instruction for every field was the same: when the entry doesn't say, answer unclear, because this would back public claims and a careful "unclear" beats a confident guess. The fields that matter here:

FieldWhat it records
Root causeOne of six layers, taken from where the entry itself says the cause lay or where the fix had to go (defined in the next section).
Caught byMe (I noticed or complained), the agent (a run, check or test found it), or unclear.
Reached meWhether the wrong output actually landed in front of me (in a briefing, the daily list, a draft) before it was caught.
PropagatedWhether the error was copied into other files or carried forward into later runs.
RepeatWhether the entry says it's a recurrence of an earlier, differently numbered entry.
Fix kindWhat was actually shipped: a rule (instruction text the runs load), code (a script, check, test or app change), both, or none.
Recurred after fixWhether the entry documents the same failure happening again after its fix had shipped.
Thin evidenceWhether the entry was too vague to classify without guessing.

The first pass covered the 292 entries logged up to 19 November. I classified the five entries logged after that with the same rubric before writing this, and corrected one older entry whose status had changed (it was reopened as a regression the same morning the first pass ran).

The check. I drew a random sample of 21 entries (three from each month with more than 20 entries, one from each smaller month, and the one entry the first pass couldn't date) and had a separate session classify them blind: same rubric, same sources, no access to the first pass's answers. Then I compared field by field.

FieldAgreedWhere they differed
Repeat21 / 21
Recurred after fix21 / 21
Caught by20 / 21The entry below.

Root cause19 / 21Two judgment calls: a config-file bug read as a tool quirk vs a model slip, and a stale channel list read as accumulation vs instructions.

Overall the two passes agreed on 175 of 189 fields (93%). Five of the 14 differences came from one entry whose write-up lives inside another entry's file. The first pass couldn't find it and marked it thin; the blind pass found it. I took the blind pass's answer for that entry. For the other disagreements I kept the first pass, so the numbers below carry roughly that much noise. Root cause agreed 19 times out of 21, which is good enough for the shares below but not for decimals, so treat ±5 points as the honest precision.

04Making things up was the minority

If you'd asked me in April, I'd have said hallucination would dominate. It's a fifth. Four in five mistakes were somewhere else: in the prompt, in my code, or in the agent treating "I didn't find it" as "it isn't there." Here's what each category means, with real examples. All of them are paraphrased and stripped of names.

Instructions (107)

The rules the runs follow were missing, wrong, contradictory, stale, or present and not applied. A rule that existed and was ignored counts here, and so does a rule that itself produced the bad output.

  • The prompt asked for "full context" on every item. So 81% of my open items started with backstory instead of the thing I had to do, and one told me to do something its own travel note said I couldn't. I left four annoyed comments in one sitting.
  • A logging step marked mandatory was skipped by eight runs in a row. Nothing checked it, so the rule only worked on the honor system.
  • A morning item told me to reply to someone and pointed me at a prep doc that held the questions. The fix was a rule: a reply item comes with the drafted reply. It went into the morning session's instructions only, and the evening session made the same mistake the next day.

My own code (65)

Bugs in Scout's scripts, parsers, schedulers, locks, exit codes and app, the plumbing I wrote around the model.

  • A commit with a misleading title rewrote the run scripts and dropped one environment variable. Logging of every connector call stopped for 17 days.
  • The retry logic had a hand-written list of "this error is temporary" phrases. It didn't include the exact wording of the session-limit message, so about a dozen scheduled runs died instead of retrying.
  • A health report decided a run had "produced nothing" from its exit code, ignoring a field that showed it had committed work. It reported 11 dead runs. Two were.

Model judgment (64)

The model inferred, assumed or asserted something the sources didn't support: invented facts, guessed names or dates, over-confident claims, misread messages, wrong priority calls.

  • A research run invented a mandatory company town hall on a specific date. The claim spread to two other files before a later run caught it.
  • For 51 days the daily list said I'd bought a piece of hardware. The evidence was a vendor's sales autoresponder, plus a second mail from the same vendor counted as an independent source. Reading the thread once would have killed it.
  • A summary of a text conversation gave my own trip to the other person, then built a second false claim on top of it. It sat in the knowledge base for nine months.

Reasoning from absence (28)

Concluding that something did not happen from an empty or partial read: "no reply," "quiet day," "not done yet."

  • A briefing told me I'd had zero Slack messages that day and guessed I'd been coding late. I'd spent 90 minutes in Slack on a production incident. The search filter it used excludes the current day.
  • A run checked Linear while another agent was still filing five issues, saw two, and put a red item on my list telling me to file the three that already existed.
  • In one morning I corrected four items that were all wrong the same way: the answer was in a thread reply, or in a correction posted a few minutes later, and the runs only read the channel's top level.

Tool or API surprises (16)

A connector behaved in a way the agent didn't expect: search semantics, pagination, a parameter silently dropped, auth.

  • Questions that needed my answer were sent as a Slack DM from me to myself, which Slack doesn't notify on. I never saw them.
  • The default Slack read format leaves out reactions. I'd answered a colleague's question with a checkmark, and the list kept the question urgent as "no reply" for five days.
  • Slack search included Scout's own messages by default, so every search term Scout had mentioned in a DM came back as a hit.

Accumulation (16)

Things that grow or go stale without anyone deciding they should: lists that only grow, facts carried forward day after day, rules that outlive their reason.

  • Every rule about volume pushed items into a "watching" tier with no cap. Open items went from 289 to 738 in 25 days. At one point the "today's focus" section held about 458 entries, and I told a session the file was unusable.
  • A line saying a pet's medication reminder was "muted, not surfaced today" was correct on day one, then copied word for word into four more daily files. The reminder never showed.
  • Two colleagues' notes still described them in roles they'd left weeks earlier. The runs had updated a status field but not the opening paragraph, which is the part I read.

05Who catches the mistakes is what changed

AprJunAugOctNov
Caught by me91%85%23%11%69%
Caught by the agent's runs2%11%66%83%31%
Reached me before it was caught98%89%70%35%77%

In April essentially every mistake landed in front of me first, and I was the one who noticed. By October most were caught by the agent's own review runs, and only about a third had reached me by the time they were caught. That's the number I'm proudest of, and it's real. It also needs three qualifications.

The agent's runs and I don't catch the same kinds of mistakes. The review runs are much better at catching bugs in the plumbing than mistakes in what the list says. Split the entries into code and tool problems on one side and everything else on the other, and the agent's share of catches in October and November is 87% for the first group but 55% for the second. The shift is real for content mistakes too (from 3% in April and May to 55%), but some of the headline comes from the review runs finding a kind of bug I'd never have seen.

"Caught by the agent" doesn't mean "caught before me." Of the 140 entries the agent caught, 60 had already reached me in a briefing or the list by the time it noticed. Only 40 were clearly caught before they reached me. The other 40 don't say.

November went the other way. I caught 9 of the 13 entries logged so far this month. Thirteen entries are too few to call a trend. But the direction is wrong, and seven of the nine are the content mistakes the review runs have always been weaker at.

What I can't claim is that it makes fewer mistakes. Better catching, unproven prevention.

I don't have a clean denominator: no count of all the items, notes and messages the agent produced, against which to measure an error rate. Logging also got more thorough over time, so the raw count of entries says as much about the logging as about the mistakes. The one prevention signal I do have is flat. The share of entries that say they repeat an earlier entry was 9% in April, 8% in August, 13% in October and 15% in November (10% over the whole log). That's not what "learning from its mistakes" would look like.

06A third of fixes didn't hold

Of the 297 entries, 109 had a fix actually shipped: a rule, code, or both. For 39 of them (36%) the entry later records the same failure happening again after the fix.

I expected "put it in code, not in the prompt" to be the clear winner. In this data it isn't: rule fixes came back 31% of the time and code fixes 29%. Fixes that needed both came back 57% of the time, probably because those were the stubborn problems to begin with, which is why they got both.

The comparison is also skewed, in a way that flatters code. The middle code fix shipped on 10 October; the middle rule fix on 14 June. Code fixes have had four fewer months to fail. You can see how much time matters by grouping fixes by when the mistake was first logged:

Mistake first loggedFixes shippedCame backShare

The spring fixes, the ones with the most time to fail, came back nearly two times in three. So 36% is probably a floor, not a settled rate: the recent fixes haven't had their chance yet. If I compare only fixes shipped before October, rules came back 36% of the time (10 of 28) and code 30% (6 of 20). That's a small edge for code, on small numbers, and still not the clear win I expected.

07As the system grew, the failures moved into my code

In the spring the top causes were the instructions and the model's judgment. By October and November, my own code was the biggest category: 26 of 59 entries. The pattern behind it is uncomfortable but simple. From September on, most of the fixes I shipped were code: a script that verifies a claim, a guard that blocks a bad write, a test. 61 of the 74 fixes that included code came in those three months. Every one of those is a new place for a code mistake. Several entries are literally a check that reported "all clear" while missing the thing it was built to catch.

The collapse of "model judgment" from 27% to 7% is tempting to read as the model getting better. Some of it may be. But the data can't show it, because who was catching mistakes changed in the same months. Model-judgment mistakes are the ones I used to catch by reading the list, and the review runs are weaker at catching them. A drop in that category in the same months I stopped catching most things myself is at least partly a drop in detection.

08The worst failures were the silent ones

None of the failures that cost the most were the model saying something false. They were the system reporting success while doing nothing.

  • An expired login failed all 21 scheduled runs over three days. Every run died at the authentication step, nothing alerted me, and the daily list I was reading was a stale copy that kept showing a finished task as overdue.
  • The evening self-review lane produced nothing for 64 days. Its "last fired" timestamp kept updating the whole time, even on runs that died within seconds, so it looked alive. The lane that processes my feedback and turns this log into fixes was the one that was dead.
  • A leftover git lock blocked every commit for three days. Runs exited cleanly and sent me summaries of work that was never saved.
  • Connector logging was off for 17 days because a commit removed one environment variable, and nothing noticed the logs had stopped.
  • A comment I typed in the app never reached the repository, and that night's briefing told me there was no new feedback.
  • A validator printed its errors and then exited with the "success" code, so the health check showed clean. After it was fixed, a plugin upgrade quietly reverted the fix.

The common thread is that every check asked "did this run exit cleanly?" or "did this tool call work?" None asked "did this capability produce anything this week?" A run can start, read everything, write files, send its summary, exit 0, and still have saved nothing.

The most expensive model-judgment mistake is the 51-day hardware purchase above. It's worth putting next to the silent failures, because it failed the same way: nothing checked the claim after the first day, so it was carried forward as true every morning until I asked about it.

About a third of all entries (106) were copied into other files or carried into later runs. Mistakes about what didn't happen spread the most (54% of them), then model-judgment mistakes (50%). Bugs in my code spread the least (22%). They break things, but they don't put false claims into the record.

09What doesn't flatter the project

Collected in one place, because it's easy to bury these in caveats:

  • Prevention is unproven. Catching improved; I have no evidence the agent makes fewer mistakes. The repeat rate is flat at about one in ten.
  • A third of fixes didn't hold, and the oldest ones came back nearly two times in three. The overall 36% will likely rise as recent fixes age.
  • "Put it in code" isn't clearly better here. Code and rule fixes came back at similar rates, and the comparison is confounded by age and by which problems got which fix.
  • Model mistakes mostly got no fix at all. Of the 64 model-judgment entries, 53 shipped nothing: the lesson was written down and that was it. It's the hardest kind to fix with a rule or a script, and the log shows it.
  • Most entries are still open. Of 297, 54 are marked fixed with nothing remaining, 67 partly fixed, 154 open, and 22 unclear. Many open entries are lessons written down with nothing shipped.
  • The self-catching number is softer than it looks. Many of the agent's catches are bugs I'd never see, and of the mistakes it caught, more had already reached me than were caught before they did.
  • The newest month went backwards, on small numbers.
  • My own code is now the biggest source of failures. Each guard against a model mistake became a new place for a code mistake.

10Caveats

  • The agent diagnosed itself. The root causes are the agent's own reading of its own mistakes. They lean toward "the rule was missing or not followed," because a rule is the fix it can make itself. Some of the 107 instruction entries are probably model-judgment or code problems seen from inside.
  • The classifier is a model too. Claude applied the rubric. The blind re-check agreed on 93% of fields, which is good but not perfect, and I didn't hand-check all 297.
  • Some entries are vague. 12 had evidence too thin to classify without guessing. 60 left either who caught it or whether it reached me unclear.
  • The log is not a census, and its thoroughness changed over time. Counts across months compare logging as much as mistakes.
  • July is nearly empty for a reason. It has five entries. The evening review lane, which does most of the self-review, produced nothing from early July to 4 September (the 64-day outage above). I can't separate "fewer mistakes in July" from "nothing was writing them down."
  • One user, one setup. This is one person's work tools, one person's tolerance for error, one person's way of complaining. Your mix will differ.

11What I'd do differently from day one

  • Watch each capability, not each run. Every check I had asked whether a run exited cleanly or a tool call worked. Nothing asked "has the self-review lane produced anything this week?" That question, asked of every lane, would have caught the 64-day outage in a day or two.
  • Record who catches each mistake, from the first one. It's the one number that moved, and the one that tells you whether the agent is earning trust. I only have it because the log happened to be detailed enough to reconstruct.
  • Decide what counts as an entry, and keep a denominator. Without a count of what the agent produced, I can say who catches mistakes but not how often they happen. A daily count of items written and claims made would have made "fewer mistakes" testable.
  • A fix isn't done when it ships. Write down what a recurrence would look like, and check for it on a schedule. A third come back, and the old ones more often.
  • Treat every new check as new code that can fail. Give it a test that proves it catches the thing it exists for, and make "I couldn't run" a failure, never an all-clear.
  • Never let an empty read stand as a fact. "I found nothing" should be stored as "I looked here and found nothing," with where and how, so the next run can tell a quiet day from a broken search.

Scout is open source (MIT) and runs on your own Claude Code login. The code, the run instructions and the rules each fix added are on GitHub. If you run long-lived agents and see the same shift from model errors to plumbing errors, or a different one, I'd like to compare notes: open an issue.

Method, briefly: 297 entries, logged 10 April to 22 November 2026, data pulled 24 November 2026. Each entry was classified by Claude against a fixed rubric from its full write-up. A blind re-classification of a random sample of 21 entries agreed on 175 of 189 fields. Percentages are rounded and carry about ±5 points of classification noise. The entries themselves contain names of colleagues and clients, so the log isn't published.
