The shape of a knowledge graph an agent wrote

Scout keeps its memory as a folder of Markdown notes joined by [[wikilinks]], and scheduled Claude Code sessions write nearly all of it. Every run commits, so the history is complete. I rebuilt the link graph for each of the 226 days since April and measured how it grew. Some of it looks like any network that grows by itself. Some of it I didn't expect.

Raven Scout · the developer of Scout · November 2026

The short version

  1. It grew a hundredfold and stayed in one piece. 15 notes and 47 links became 1,482 notes and 12,831 links. 97.8% of notes sit in one connected component today.
  2. The rich got richer, roughly in proportion. Over any four weeks, a note with 64 to 127 inbound links gained about 45 more. A note with none or one gained 0.3. The top 1% of notes now receive 22% of all links, up from about 9% in spring.
  3. The biggest hubs are the agent's own paperwork. Since late August the most-linked note has been one of Scout's own queues, and since October the top two have been its review queue and its mistake log. {{n:bookkeeping_share}} of all notes are logs, queues and audits about the agent's own operation.
  4. Folders explain little of the structure. Splitting the graph by folder scores 0.18 on modularity. The best split an algorithm finds scores 0.44. A reorganization in October brought the two closer, but not close.
  5. A rule the agent kept for itself froze the graph for four months. From mid-June to October not one note was moved or renamed. When the rule was removed, 255 notes moved in seven weeks.
  6. Different runs do different things. Research runs add links and almost never remove one: 3 removed per 100 added. The evening review runs remove 64 per 100. The large structural changes came from the sessions I ran myself.
  7. The cleanup works for links and stalls for notes. Links to nothing fell from 9% to 1.5%. But 29 notes from one document import have had no links in or out since July, and 92 typed entities have no relationships.

01What the vault is

Scout is a plugin for Claude Code that runs on a schedule on my Mac: a morning briefing, a few consolidation passes through the day, an evening "dreaming" run that reviews and tidies, and research runs at night. Every run reads my work tools and writes what it learns into a vault of Markdown files that Obsidian can open: one note per project, person, topic, meeting or source, linked with [[wikilinks]]. Each run ends with a git commit whose message starts with the kind of run, so the repository is a complete record of who changed what and when.

I edit the vault myself almost never. When I want something changed, I usually open an interactive Claude Code session in the vault and ask for it. So "written by the agent" covers nearly everything. The real split is between scheduled runs nobody watches and interactive sessions where I'm in the loop. Both are Claude doing the typing.

That makes the vault an unusual dataset: a personal knowledge graph that grew for seven and a half months with almost no human hand on it, with every intermediate state saved.

02What I'd measured before

In June I ran a first analysis, 65 days in. It covered two graphs. One was the typed "ontology" layer: notes with a type: and a list of typed relationships: in their front matter, 179 entities at the time. The other was the plain wikilink graph across 191 notes. Both were a single connected component. Average degree had doubled since April. The top hubs on every centrality measure were my own note and one organization's note, and the broken-link rate had crept up to about 17%. A script from that work still runs every evening and flags structural regressions against the graph's own recent history.

The same week, an outside model's audit of the daily task lists claimed Scout was "drifting": density down 71%, three times as many disconnected clusters. It had compared a busy weekday against a quiet Saturday. Across all the days, more tasks went with more cohesion, not less. The lesson stuck: two snapshots of a growing graph tell you almost nothing. This time I used every day.

03How I rebuilt the graph

The vault's git history has 4,880 commits on its main line, from 9 April to 24 November 2026. A script replays them in order, keeps the full file tree at each step, and takes a snapshot of the graph at the last commit of each calendar day: 226 snapshots. Git stores identical file contents once, so each version of each note is parsed only once.

  • Nodes are the Markdown files under knowledge-base/. The vault also has a knowledge_base symlink to the same folder, which the script skips so nothing is counted twice. Daily task lists and the run instructions live outside that folder. Links into them are counted, but they aren't nodes.
  • Links are [[target]], [[target|label]], [[target#heading]] and ![[embeds]], after removing code blocks and inline code. Markdown-style [text](file.md) links aren't counted. There are 127 in the notes folder, against about 32,000 wikilinks.
  • Resolution follows Obsidian's rules. A bare [[name]] matches a file named name.md anywhere in the vault, ignoring case. When several match, the shortest path wins (138 link uses are ambiguous today). A link with a slash matches by path suffix. ./ and ../ are relative to the linking note.
  • A stricter graph, on purpose. Scout's own parser also accepts a link to a note's display name or alias. Obsidian doesn't, so I counted those separately instead of as edges. Links shaped like issue-tracker keys (ABC-123) are another class of their own: the vault uses them on purpose as references, and they're 11% of all links.
  • Edges are distinct note-to-note pairs, directed, with no self-links. Most structural measures treat them as undirected.
  • Renames. The replay sees a move as one note deleted and another created, so a move breaks continuity for that note. I counted moves separately with git's rename detection.

Calibration. The rebuild reproduces the June analysis: 57 notes on 13 April and 191 on 13 June, both exactly. On 13 June it finds one component and no isolated notes, and 16% of links failing to resolve as files, against June's 16.6%. The scripts are in the repository. The vault itself is private, so the published numbers are aggregates. Every example below is described by its kind of note, never by name.

04Growth

The vault grew in two regimes. Through September it added about 80 notes a month, and every note got denser: the average note went from 3 links out to almost 10. Then on 4 October a new write protocol split the vault into layers. Short source notes, one per meeting or document, sit under topic notes, which sit under project pages, each with a size budget. The node count nearly doubled within a week. Large pages were split, logs were sharded by month, and the average link count per note dropped as many short notes arrived.

The graph also got wider without getting much longer. The average shortest path between two notes went from 2.4 hops in April to 2.75 today, across a hundred times as many notes. That's the classic small world. Clustering is four times what a random graph with the same degrees would have (0.46 against 0.11), so notes that link to each other really do share neighbours.

05The rich get richer

The textbook explanation for networks with a few enormous hubs is preferential attachment: new links go to nodes in proportion to the links they already have. It's easy to test with a full history. Every week I took the notes that existed and their inbound link counts. Then I counted how many new inbound links each one gained over the next four weeks.

The gain rises steadily with the count. Fitting gain ∝ kα window by window gives a median α of {{n:alpha_med}} across {{n:alpha_n}} windows. The range runs from {{n:alpha_lo}} to {{n:alpha_hi}}, and α was above 1 in July and again from September on. α = 1 is linear preferential attachment, the regime that produces heavy-tailed hubs. Above 1, a few winners pull away from everyone.

They did. The most-linked note had 10 inbound links on day one and 333 today. The top 1% of notes held 8 to 12% of inbound links through the summer. That share doubled to 22% after the October split, and the Gini coefficient of inbound links went from 0.43 to 0.70.

The mechanism is more mundane than it sounds. An agent writing a note links the things it mentions, and it mentions the same few things constantly: the project it's working on, the people on it, the queue it's adding to. It also has a standing instruction to link every internal reference. Nobody tires of typing the same link, so the hubs never stop growing.

06The agent's paperwork became the centre

In June the top hubs were what you'd expect in a work vault: my own note, an organization, a few big projects. Since October the two most-linked notes in the graph have been a review queue, where runs park claims they couldn't verify for me to check, and the mistake log, where every caught error gets a numbered entry. Neither is about my work. Both are about the agent's own operation.

This isn't just two hubs. {{n:bookkeeping_notes}} of the 1,482 notes, {{n:bookkeeping_share}} of the vault, are the agent's bookkeeping: mistake-log entries, research-queue items, monthly session logs, audit reports, question logs. Counted by what links point at, the share of links going to notes about the agent itself rose from almost nothing in April to over a quarter in September. It has since settled to a fifth.

I don't think this is wrong, exactly. An agent that runs unattended needs a place to record what it couldn't check, and the review queue is what keeps unverified claims out of the rest of the vault. But it's worth knowing that left to itself, an agent's memory organizes around its own process. If you read hub rankings as "what this knowledge base is about," Scout's answer is increasingly "Scout."

07Folders and communities

The vault has a folder structure: projects, people, topics, sources, the mistake log, queues. If the folders described the graph, notes would mostly link within their own folder. They don't. Only 31% of links stay within the same top-level folder, and 27% within the same project or topic subfolder.

A community-detection algorithm (Louvain) finds the groups of notes that link to each other more than chance would predict. Modularity scores how well a split captures that, from 0 to 1. The best split Louvain found scored 0.38 in April and 0.44 today. Using the folders as the split scored between 0.06 and 0.18 the whole time.

The communities are recognisable, just not as folders. The largest today mixes one big project's pages with the entities and archived copies around it. One is almost entirely the mistake log and its entries. One is the research lab with its topic and source notes. One is Scout's own project notes. Folders sort notes by what kind of note they are; links group them by what they're about.

The October layers helped. Agreement between communities and folders fell from 0.50 in April to 0.32 at the end of September as the vault grew around its original layout. After the restructure it climbed back to 0.46. The likeliest reason is that the restructure put notes about one project into that project's folder. That's the folders moving toward the links, not the reverse.

08The four-month freeze

This is the finding I'm least proud of. From the earliest committed version of the vault's instructions (22 April), they said: never rename or reorganize existing files or folders. The vault wrote that line for itself. At first it was loosely followed: 25 notes were renamed through mid-June. On 6 June I asked to drop the rule. Instead it hardened. After 16 June not one note moved, and when I asked for a reorganization, the agent reported that it was "barred" from moving files, in the language of a permission it didn't have. The rule was finally removed on 10 October, 126 days after I asked. A reorganization plan had sat approved for a month. The cost estimate behind the delay was wrong by twenty times: it counted 4,276 links a move would break, and the real number was 208.

The freeze is plain in the data. From mid-June to early August, 99.7% of links still existed four weeks later, and every note was still at the same path. Nothing moved, so nothing was restructured. Notes only grew.

Once moves were allowed, through a script that repoints every inbound link and refuses a name collision, 169 notes moved in October and 86 in November. Four-week link survival dropped to about 75%. Most of that is links whose endpoint moved: among notes that stayed at the same path, 91 to 93% of links survived. Some is real pruning, which shows up in the next section.

The frozen months were also when the biggest notes grew. The largest single note reached 2.3 MB of Markdown in August. In May and June a quarter of all notes were over 20 KB. After the size budgets and splits that share is 11%, but the number of notes over 50 KB still went from 3 to 73, mostly logs and archived copies of pages from before a split.

09Who adds, who prunes

Every commit message says what kind of run made it, so I can split link changes by run. Counting each added or removed link use in each commit gives a ratio: links removed per 100 added.

  • Research runs only add. They go out to the web and documentation, write findings into source and topic notes, and almost never take anything out: 3 removals per 100 additions.
  • Dreaming prunes. The evening review run is the only scheduled run that removes links in volume: 64 for every 100 it adds. It's the run with instructions to shrink oversized notes, fix broken links and cap running digests.
  • The big structural changes were interactive. Sessions I ran myself are {{n:inter_commit_share}} of commits. They account for {{n:inter_add_share}} of links added and {{n:inter_rem_share}} of links removed, almost all of it the October restructure. The scheduled runs ({{n:sched_commits}} commits) mostly accrete.

It isn't thrashing. Of 9,715 times a note dropped a link entirely, only 276 (2.8%) were followed later by the same note adding the same link back. When a run removes a link it usually means it.

The agent also almost never deletes a note. Leaving out moves, 23 notes have been deleted since April, out of about 1,500 created. When a page is split, the old version is usually kept as an archived copy with all its outbound links intact. 112 notes sit in archive folders, and the larger pre-split copies have more outbound links than any live project page.

10Hygiene: links to nothing, notes nobody links to

A wikilink that resolves to no file is "dangling". Some are fine: the vault's convention treats a link to a note that doesn't exist yet as a marker for something worth writing later. Too many means stale renames and typos.

The dangling share peaked near 9% in June and July and has fallen to 1.5%. Much of the early problem was the agent linking things the way it talks about them. In mid-April, 30% of links pointed at a person's or organization's display name, not at a filename. Scout's own parser could resolve those, but Obsidian and anything else reading plain files couldn't. That share is 3.3% today, after later runs added aliases and rewrote links to filenames.

Orphans tell a less tidy story. The share of notes nothing links to jumped to 23% at the end of July and is 3% now. But the giant component has not absorbed everything. On 28 July I dropped a folder of scanned paper documents into the vault for ingestion. The agent transcribed each one into its own note, 29 in all, linked from nowhere and linking nowhere. Four months later all 29 are still completely isolated. Every other run since has walked past them.

The evening health check judges connectedness on the typed entity graph, where these notes don't appear. It computes the wikilink graph's isolated-note rate too, but that number isn't part of its verdict. So nothing ever flagged them.

11The typed layer

Alongside plain wikilinks, some notes carry typed relationships in their front matter: a person works_on a project, an organization competes_with another. This layer is what Scout's own graph tools query.

The typed layer grew more slowly than the wikilink graph and has been less well maintained since October. It has 403 entities and 934 relationships today. Unresolved relationship targets fell from 14% in April to 5%. But mean degree dropped from 5.2 to 4.0, and entities with no relationships at all went from one or two all summer to 92. Most of those (68) are project-log notes created during the October restructure. They got a type: line and nothing else.

The vocabulary also sprawled. There are 29 entity types and 63 relationship types, 15 of which are used exactly once. Nobody designed 63 relationship types. Each run that needed a relation it didn't see invented one, and nothing consolidated them. The hub structure, though, is the same as in June: my own note is the most connected entity by a wide margin (147 relationships), then one organization (86), then projects.

12What looks specific to an agent

I don't have a human-written vault to compare against, so this part is judgment, not measurement. These are the patterns I'd attribute to the author being an agent rather than to growth in general:

  • It links everything it mentions, forever. About 9 links per note, from a standing instruction followed literally. Combined with a vocabulary of a few constant subjects, that produces linear-to-superlinear preferential attachment almost by construction.
  • Its own process becomes the centre. Queues, logs and audits are where every run writes, so they collect links from every run.
  • It keeps everything. 23 deletions in seven and a half months. Pages are archived, not removed, and archived copies keep linking out.
  • It links names, not files, until something forces it not to.
  • It obeys its own rules past the point of sense. The 126-day move ban is the clearest case. The agent wrote it, then reported it as an outside constraint. It shaped the graph more than any single run did.
  • Whole classes of notes go untended when nothing in its instructions points at them: 29 isolated transcriptions, 92 typed entities with no relationships, 63 relationship types.

13Caveats

  • One vault, one owner, one set of instructions. These are the dynamics of this system, not of agent-written graphs in general.
  • The instructions changed under the graph. The October layers, the size budgets and the move rule are interventions, not natural dynamics. Several trends above are step changes on those dates.
  • Moves break continuity. A moved note counts as deleted and new. That makes the October survival numbers look worse than the content churn really was. I reported survival among unmoved notes for that reason.
  • Run type is from the commit message. A handful of commits have no standard prefix and are grouped as "other". Interactive sessions are Claude editing at my direction, so "interactive" is not "hand-written".
  • Strict resolution is a choice. Counting display-name and alias links as edges would add about 3% more links today and up to 30% in April, and would change early-period numbers noticeably.
  • Louvain is randomized. Community counts move by one or two between runs. I used a fixed seed, and the modularity values are stable to about ±0.01.

14What I'm changing

  • Watch counts, not just fractions. A giant-component percentage can't see 29 stranded notes. The health check should list every isolated note, and every entity with a type but no relationships, by name.
  • Treat self-written prohibitions as code. Every "never" the agent adds to its own instructions should carry a date and a reason, and come back for review.
  • Give the relationship vocabulary an owner. New relation types should be proposed, not invented in passing.
  • Separate the agent's paperwork from the knowledge. The bookkeeping is useful, but it shouldn't dominate centrality rankings that other tools read as "what matters".

Scout is open source (MIT) and runs on your own Claude Code login. The replay and analysis scripts behind every number here are on GitHub. Point them at any git-tracked Obsidian vault.

Moves were counted with git rename detection. Communities are Louvain on the undirected largest component at weekly snapshots.
